# TRIPPED! performance pass (G7), 2026-10-24

Unity 6000.3.8f1, URP (PC_RPAsset, Forward+), editor Play mode. The Day level ("One Busy Day", level 100) was started
with `ScreenFlow.StartDemo()` and played for 60 s after a 3 s warm-up. The commands were the ones the keys send, put in
through `LevelController.Submit`, in a fixed 8 s cycle: Walk +1, stop, Interact, Climb +1, Walk -1, stop, Interact,
Climb -1, Interact. 55 commands were accepted and 16 refused, the same in every run.

**Conditions.** Every number here comes from the editor, so editor overhead is included (EditorLoop alone is about
7–8 ms of each frame). The frame rate was uncapped (`targetFrameRate -1`, `vSync 0`) for all runs. The Game view was
601x423. GPU time comes from `FrameTimingManager`. Batches, SetPass, tris and verts come from `UnityStats` (Game view).
GC data comes from the `GC Allocated In Frame` recorder plus `GC.Alloc` samples in the profiler hierarchy, taken over 141
profiled frames. Read the before/after columns side by side; don't treat them as player numbers. A Development build
was not measured (see "Not done").

The "before" run already includes G6's uncommitted UI work as of 20:12. G6 kept changing UI/HUD files between runs, so
small differences in HUD cost are not mine. Raw output: `perf-before.txt` and `perf-after2.txt` in the G7 scratchpad
(the numbers below are copied from them).

## Changes and their measured effect

1. **Main light shadows off** (`Main.unity`, Directional Light, Shadows Soft → None). The ortho camera sits at z = −50
   and the house starts at z = 0, while the URP shadow distance is 50. Every shadow caster was rendered into 4 cascades
   of a 2048 map each frame, and the result was never seen. A 1280x720 render with shadows on and off came out
   identical: mean diff 0.000, max 0. This is where most of the drop in batches (457 → 255), tris (−51 %) and GPU time
   comes from. **If art wants visible shadows:** set shadow distance ≈ 60 with 1 cascade and turn the light back on.
   That changes about 60 % of pixels (measured), so it is a look decision, not a perf one.
2. **SSAO renderer feature off** (`PC_Renderer.asset`). It cost a full-resolution depth-normals prepass (a second pass
   over every mesh) plus the AO and blur passes. Its visible contribution was mean 0.155/255 per channel, max 12/765
   summed over RGB, and 0 % of pixels changed by more than 4 levels per channel. Negligible.
3. **URP asset** (`PC_RPAsset.asset`): Opaque Texture off, Depth Texture off, HDR off. Each one gave an identical
   1280x720 image (max diff 0). With no post-processing and no shader sampling those textures, they were pure copy and
   bandwidth cost.
4. **Room textures max size 1024 → 512** (`Art/Models/Textures/*.png.meta`). They were already DXT1 with mipmaps. At
   1920x1080 the diff against 1024 was mean 0.14/255 (overview) and 0.46/255 (2x closer than the follow camera), with
   0.01–0.05 % of pixels over 8 levels. Saves about 11.5 MB of texture memory.
5. **Model import** (`HouseKit.fbx`, `Room_*.fbx` .meta): Rig Generic → None, import animation, cameras, lights and
   blend shapes all off. The files contain none of these. The rig was adding an Animator and Avatar to every instanced
   room model. Measured 0 Animators after. Read/Write was already off.
6. **`SoundBank` synthesises in the background** (`Juice/SoundBank.cs`). The constructor now only looks up files. A
   ThreadPool worker generates the non-music sounds, UI sounds first. Music tracks are made only when first asked for,
   through the new `IsReady(name)`. Clips are created on the main thread at first `Pick`. A sound picked before the
   worker reaches it is made on the spot, so `Pick` still never returns null for a known name. These stay the same:
   sound names, `Resources/Audio/{name}` file overrides and `{name}_N` variants (`IsFromFile`), and `SynthBank.Generate`
   with its output. Boot cost: 399 ms → 2.6 ms.
7. **Music switch waits for readiness** (`Juice/JuiceController.cs`). A new track starts when `Bank.IsReady(track)` is
   true; until then the old one keeps playing, a frame or so. The two music sources are created without picking a clip,
   so `music_day` is no longer synthesised on the boot frame.
8. **Per-frame allocations removed** (zero-alloc rule):
   - `World/RoomView.Sync`: the room label ("Kitchen 6/8") and the trip countdown were rebuilt as strings every frame
     for all 7 rooms. They are now rebuilt only when load, capacity, on/off or over-ticks change.
   - `Art/ArtLibrary.CharacterFrames`: built a path string every frame, twice when it fell back to idle. Now cached by
     state.
   - `Logic/DayRules.IsBlackout` and `ActiveCount`, `Logic/DayInteraction` (runs every frame for the key prompts),
     `World/HouseView.SyncCables`, and `JuiceController` appliance and spark loops: `foreach` over `IReadOnlyList<T>`
     boxed an enumerator each call. They are indexed loops now.
   - `JuiceController`: `SynthBank.LoopOf(type)` string concatenation per working appliance per frame is cached, and the
     `Find("Character")` lookup each frame is cached too.
   - Result: `HouseView.LateUpdate` went from 1 994 B / 44 allocs per frame to 40 B / 1 alloc per frame.
9. **Frame pacing** (`Config/TrippedViewConfig`: `targetFrameRate = 60`, `vSyncCount = 1`, applied in
   `Core/GameRoot.Awake`). Before, the game ran uncapped (`targetFrameRate -1`, vSync 0). That spins the GPU and CPU
   at 100+ FPS on weak hardware for no visible gain. Both values are data-driven in the view config.

## Not changed, and why

- **Static batching / mesh combining per room.** The SRP Batcher is on and SetPass is already low (24). Static
  batching keeps a combined copy of every mesh, about +12 MB on a machine that is short of RAM. It was not worth it
  after the shadow and SSAO cuts.
- **Sharing the 73 embedded materials across FBXs.** The SRP Batcher batches by shader variant, not by material
  instance, so the per-FBX copies don't break batching. Remapping them is a risky art-pipeline change for little gain.
- **Normal maps imported as "Default" texture type (sRGB) instead of "Normal map".** This is a correctness issue for
  art, not perf. Fixing it would change how lighting looks and double their memory (BC5). Flagged below.
- **Appliance sprites (512 px, DXT5, no mips, 256 KB each, 10 sprites ≈ 2.5 MB).** Already compressed. An atlas would
  save little and could change the look.
- **Procedural sample rate stays 44.1 kHz.** Lowering it would dull the hi-hat and kettle hiss, which changes how they
  sound. Total synthesised audio is only about 8 MB.
- **Particles / CameraShake / ScreenFx.** Particles were already pooled with a cap. ScreenFx disables its full-screen
  images at alpha 0, so there is no overdraw when idle. CameraShake's only allocation comes from G6's `UserSettings`
  (below).
- **`FeedbackController.EnsureListener`.** One `FindObjectsByType` array per second, about 1 alloc/s. G6 is editing
  this file, so I left it.
- **Remaining 44 B/frame in `HouseCamera.LateUpdate` and about 110 B/frame in `LevelController.Update`.** The latter
  comes from sim tick events (Scripts/Sim, off limits). The `HouseCamera` alloc was not pinned down; it is the same in
  every run.
- **Development build to `D:\unity\TRIPPED_perfbuild`.** Skipped. A URP player build (shader variant compilation) takes
  several minutes and a lot of RAM on a machine whose page file filled up today, and G6 was waiting on the editor lock.
  Recommended as the next step: start the build with `-startLevel 100` and read the same numbers there.
- **Play → Title wall time.** It can't be separated from the editor's domain reload in Play mode. The part the game
  controls, `SoundBank` synthesis, went from 399 ms to 2.6 ms of main-thread time.

## HUD / UI items for G6 (not edited by me)

1. **`Hud.LateUpdate` allocates 1.5–2.4 KB / about 40–60 allocs every frame**: the biggest per-frame allocator left in
   the game. Typical causes:
   - Text set every frame. For example `DayStatus`: `_time.text = second / 60 + ":" + ...` — check it is guarded by
     "changed".
   - `foreach` over `sim.Requests` / `sim.Rooms` (boxed enumerators) in `DayHud.cs` lines ~115, ~500, ~631/634 and
     `PowerPanel.cs` ~66 — use indexed loops.
   - String formatting in ticket and meter `Sync`.
2. **`UserSettings.GroupFactor` / `CameraShake` (`ShakeEnabled`) hit PlayerPrefs and build strings on every call.**
   `Volume()` does `Prefix + "vol." + channel` (enum ToString, two concatenations) plus a native `PlayerPrefs.GetInt`.
   It is called from `FeedbackController.VolumeFor`, which runs every frame for the music, each appliance loop and each
   hum, and `CameraShake.LateUpdate` calls `ShakeEnabled` every frame. Measured: 66 B/frame in CameraShake and most of
   the remaining 157 B/frame in JuiceController. Fix: cache the values in fields, refresh them in `Set`.
3. `TuningPanel.OnGUI` (editor and dev builds only) costs 368 B and about 0.13 ms every frame even when closed. It is
   not in release builds.

## Risks

- **Threading:** `SoundBank` now uses one ThreadPool work item (plus one per music track on demand).
  `SynthBank.Generate` is pure: it allocates its own buffer and uses a per-call seeded `System.Random`, so its output is
  the same as before. Shared state is guarded by a lock. On a platform without threads (WebGL), `QueueUserWorkItem`
  failing is caught and every clip is made synchronously on first `Pick`, which is the old behaviour minus the boot
  hitch. On WebGL, `IsReady` would keep returning false for music; this does not affect the Windows build.
- **Music start delay:** the first track can start up to about 0.2 s later than before (menu music synthesis). It fades
  in, as before.
- **Shadows/SSAO off** means a future camera or light change will not bring shadows back by itself. See change 1.
- **`PC_Renderer.asset` serialization:** saving upgraded the asset (`m_AssetVersion` 2 → 3, debug-shader refs
  re-flowed). This is a normal URP upgrade; it is also used by `Assets/Scenes/SampleScene.unity`.
- **G6's UI changed between the before and after runs,** so the HUD rows in the table are not a clean A/B. All the
  rendering, GC (World/Juice) and audio rows are.
